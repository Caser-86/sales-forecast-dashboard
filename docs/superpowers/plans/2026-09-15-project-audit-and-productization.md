# 1. 项目概述

项目提供商品/门店历史销量、未来 30 天预测、KPI、品类占比、Top 商品、ABC 热力图。主要用途是展示零售预测的数据处理、机器学习、API 和可视化工程链路。

当前不是空壳：模型训练、推理和 API 聚合确有实现，已有自动化测试。但数据来自生成脚本，采购量来自固定倍率，缺货风险来自 ABC 等级，缺少库存事实、可保存的业务结果和可信的多步回测。因此更准确的定位是：**工程化 Demo / 面试型 MVP，不是可直接指导采购的生产产品。**

真实用户链路现状：进入页面 → 选择范围 → 查看历史与预测基本成立；理解指标 → 判断是否可信有断点；生成补货单 → 保存 → 再次查看 → 追溯版本尚未实现；服务失败后重试与旧数据辨识也不完整。

# 4. 当前架构

```text
生成脚本 -> raw CSV -> 特征CSV -> 时间切分 -> LSTM + LightGBM
                                      -> 权重/scaler/报告（分别覆盖）
浏览器 -> API路由 -> data_service -> 缓存CSV/报告
                -> forecast_service -> 线程池 + LRU -> Predictor单例
                                                    -> 固定路径模型/历史
                -> inventory_service -> ABC/经验倍率 -> 热力图
```

优点：API 与基本服务分层，ABC 提取为共享函数；预测器单例有初始化锁，批量结果有稳定顺序；不是所有请求都重新加载模型。

薄弱点：API 聚合仍包含业务规则；模型文件、报告和历史没有共同版本；配置层与 ML 常量两套来源；缓存没有数据更新协议；前端状态由多个异步函数分别修改，缺少请求一致性约束。

RAG、Agent、Tool 调用、向量库均不存在，也不应作为本项目“缺失的必选层”。没有真实数据库查询，因此不存在可供优化的 SQL/N+1 查询链路。

# 9. 代码质量问题

职责大体清晰，没有证实循环依赖或常态内存泄漏。不建议全面重写。

主要问题是契约与状态而非语法：大量 `dict[str, Any]` 跨层传递，导致前后端字段不匹配；窗口/权重/阈值/倍率散落；不同异常路径使用不同响应形状；catch后返回成功形态使业务错误被掩盖。

数据读取、校验、派生查询混在data_service；预测器同时承担加载、特征递推、ABC和采购建议。应把输入数据/模型包与领域计算分离，但不需要每个函数单独建类。

`lru_cache`有容量上限，不等于泄漏；问题在失效、重复并发计算和容量与商品门店数不匹配。线程池上下文会关闭线程，不能无依据称未释放资源。日志已有请求ID和耗时，但模型/数据版本、预测失败数与请求关联不充分。

# 10. 架构问题

推荐目标：

```text
受控CSV导入CLI -> schema校验 -> 不可变dataset_version
离线训练/回测 -> manifest + 模型/scaler/编码器/报告 -> model_version
人工发布/回滚 -> 校验完整包 -> 原子切换active引用
FastAPI -> 明确数据快照 -> 共享预测服务 -> 版本化缓存
        -> 补货规则 -> SQLite草案/导出记录（单租户）
前端 -> API单一契约 -> 请求序号/取消 -> 正常/部分失败/过期状态
```

值得现在调整：配置单一来源、ML/数据包版本、失败语义、共享未来特征。这些会直接影响正确性。

暂不值得：微服务、事件总线、分布式缓存、Kubernetes、全功能模型平台。一个manifest、一个active指针、人工发布、单进程共享并发限制可以满足第一版。

风险控制：保留旧API兼容读取期；用fixture锁定输出；模型格式变更时重新生成验证产物；数据发布不原地覆盖；旧版本可回滚；先完成下游测试再移除兼容导出。

# 18. 成品必须补齐的能力

建议V1明确为：**单租户、单部署实例、受控CSV数据源的需求预测与补货辅助工具，最终采购由人确认。**

必须有数据导入验证、版本标识、有效预测/基线、输入假设、非伪造的不确定性表述、库存事实、补货解释、草案保存/导出、异常可见、权限边界、备份恢复。

最小补货公式建议以“交期+复核周期”为需求窗口：

```text
净可用 = 在手库存 + 已确认在途 - 已预留数量
目标库存 = 窗口预测需求 + 明确配置的安全库存量
原始补货 = max(0, 目标库存 - 净可用)
建议量 = 原始补货为0则0，否则按包装倍数向上取整且满足MOQ
```

交期超过已支持预测周期时明确拒绝计算或显示需要更长预测，不能截断后继续输出看似有效的建议。安全库存可先采用人工配置，必须标注“人工政策”，不假装统计最优。

如选择仅做“需求预测查看器”，可以合法缩小范围，不实现补货草案；但必须从产品定位中移除库存风险和采购建议承诺。本文主计划按保留现有补货定位编写，实施前由TASK-001冻结。

12. 断网/超时/乱序/恢复/空数据有真实状态；页面无未处理异常和undefined字段。
