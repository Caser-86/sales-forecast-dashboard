# 12 分钟面试演示

目标：让面试官看到一条可解释的「数据 → 预测 → 补货 → 审批 → 恢复」业务闭环，并能追问到设计取舍和验证证据。页面顶部的「演示路线」与本稿顺序一致。

## 面试前准备

1. 按 [README](../README.md) 完成依赖安装与 `prepare_demo.py`。现场使用已经准备好的包，避免等待全量训练。
2. 用 `scripts\start_demo.ps1 -Root .demo-runtime -WithAuth` 启动，浏览器打开 `http://127.0.0.1:3000`。端口冲突时同步指定 `-BackendPort 18026 -FrontendPort 13026`，打开前端端口即可。
3. 管理员登录，确认系统页场景为 `standard`、健康可用；如需切换场景，在页面确认实际影响。先备份当前演示状态。
4. 准备一份错误 CSV 和一份通过预检的 CSV；可从数据中心下载模板。核对本轮演示的数据版本与业务日期，不背固定指标数字。
5. 选择一个有库存风险、预测覆盖完整的商品/门店。实际试走一次创建、提交、审批和导出。
6. 演示 1366×768 或更大窗口；桌面可收起路线腾出空间。模型训练、重建资源与依赖下载放在面试之前完成。

完整自动回归可执行 `scripts\verify_offline_demo.ps1 -Root .demo-runtime -RunFullReplayE2E`，它会恢复标准场景并创建测试记录。它不能替代 [T10 人工断网验收](t10-manual-evidence-template.md)。

## 现场顺序

| 时间 | 页面与动作 | 要讲清楚的内容 |
| --- | --- | --- |
| 0:00–1:00 | 经营总览，说明数据来源与业务日期 | 生成数据用于验证流程；历史与预测窗口、商品/门店范围保持一致 |
| 1:00–2:30 | 管理员在数据中心预检错误 CSV，再保存有效候选 | 行级错误可定位；坏数据与候选数据不会直接覆盖活动快照 |
| 2:30–4:00 | 模型中心查看活动策略、候选指标和训练任务 | 训练与发布分离；验证集选策略、测试集评估；基线胜出也接受 |
| 4:00–5:30 | 预测分析下钻同一个商品/门店 | 历史与未来 30 天明细、指标窗口与来源版本；情景范围不是置信区间 |
| 5:30–7:30 | 换分析员，库存决策筛选风险、试算并创建草案 | 需求窗口、可用库存、在途、安全库存、MOQ 和包装取整；调整有原因 |
| 7:30–9:30 | 计划中心提交，退出后用审批员批准并导出 | 服务端校验角色；提交冻结版次；批准不等于已采购或已到货 |
| 9:30–11:00 | 管理员看审计，切换库存过期，再恢复标准场景 | 过期来源阻止业务操作；恢复与错误输入都有明确结果 |
| 11:00–12:00 | 系统页看诊断与备份，结束讲解 | 可追溯版本、受控日志与恢复能力；说明生产化边界 |

角色账号见 [README](../README.md)。页面切换账号需要退出并重新登录，不能把前端显示身份当作授权。

开场可以这样说：

> 这是一个面向零售补货的本地决策工作台。我把需求预测接到库存试算与审批流程，并给数据、模型和计划保存来源版本。当前使用生成数据，因此我展示的是工程闭环与验证方法，不声称已经提升真实业务收益。

只有 5 分钟时，缩短为：总览说明问题 → 预测解释口径 → 库存试算 → 计划审批 → 异常拦截与边界。数据导入和训练细节留在追问环节。

## 值得讲的三个设计

**发布是一致状态切换。** 销售数据、库存和模型分别有版本，但业务读取的是兼容运行快照。候选训练固定输入，失败不会自动覆盖活动模型；发布前校验兼容性，支持人工回滚。

**审批是一条可追溯状态机。** 草案、提交、批准/驳回和修订有服务端约束。乐观版本号处理并发冲突，幂等请求避免重复动作，审计保存来源和策略版本。

**展示结果必须能解释。** 数据按时间切分，候选策略在相同 origin/horizon/商品门店集合上比较。WAPE 用于选择，MAPE 和 RMSE 提供不同视角；不把生成数据上的指标外推成生产收益。

## 常见追问

| 问题 | 回答要点 |
| --- | --- |
| 为什么不随机切分？ | 预测面向未来，按时间切分减少未来信息泄漏；validation 选策略，test 保留为最终评估。 |
| 为什么保留朴素基线？ | 复杂度不是收益。与前一周同日销量比较，才能判断模型是否值得发布。 |
| MAPE 为什么不能单独看？ | 实际销量为零或接近零时不稳定；解释有效样本，结合 WAPE/RMSE，并按业务场景分层。 |
| 训练会不会阻塞页面？ | 独立子进程执行，SQLite 保存阶段和心跳；候选隔离，后台训练期间已有服务继续工作。 |
| 两个审批员同时操作呢？ | 服务端校验版次；重复同动作具备幂等性，冲突动作要求刷新后再处理。 |
| 为什么用 SQLite 和文件？ | 单机演示部署成本低且易复现；事务记录业务状态，版本化文件存放资源。多实例时需要重新设计共享存储与任务队列。 |
| 如何验证？ | 后端业务/迁移测试、真实浏览器流程、Windows 启停检查和故障回归。展示对应提交的 CI 和带日期的验收记录。 |
| 离生产还差什么？ | 真实数据契约、企业身份与密钥、持续训练/漂移监控、容量与恢复目标、多实例运维。 |

## 现场故障处理

- 端口占用：先停止自己的演示实例，或换一组端口；不要结束不属于本项目的进程。
- 页面报后端不可用：查看演示目录 `logs/backend-error.log`，核对健康接口；修复后重启，不把失败页面解释成成功。
- 库存过期导致操作被阻止：核对是否停留在异常场景，管理员通过系统页恢复标准场景。
- 时间不足：展示已完成训练的真实结果，省略现场长训练；审批与异常拦截优先于逐页展示。

演示结束运行 `scripts\stop_demo.ps1 -Root .demo-runtime`。代码与验收事实参考 [V2 记录](local-demo-v2-acceptance-2026-09-22.md)，固定参考机及人工断网验证按原计划继续保留待验收状态。
