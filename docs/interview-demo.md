# 5 分钟面试演示稿

这份稿子用于配合 README 和运行中的 Dashboard。目标是讲清楚“业务问题、技术方案、验证证据、生产边界”，而不是逐文件念代码。

面试前先按 [`docs/deployment-checklist.md`](deployment-checklist.md) 完成启动和浏览器检查，避免把排查环境问题的时间放进正式演示。

## 0:00-0:30 项目定位

> 这是一个零售销售预测 MVP。业务目标是把未来 30 天的需求预测转成补货参考，同时让业务人员能按商品和门店查看结果。当前使用生成数据，重点展示的是完整链路和工程质量，不把示例指标当成生产效果。

## 0:30-1:20 业务链路

打开 Dashboard，先说明默认全量视图：

- KPI 的历史销量是最近 30 天，预测销量是所有商品和门店未来 30 天预测的汇总。
- Top 商品的预测值会把该商品在所有门店的预测相加，避免商品粒度和门店粒度混用。
- 库存热力图用 ABC 分类和建议采购量标记风险，服务于“先补什么货”的决策。

## 1:20-2:20 交互与 API

1. 在顶部选择一个商品和门店范围。
2. 说明 KPI、品类、Top 商品和库存热力图同步变化。
3. 在趋势图中切换单商品/门店，展示历史销量、预测销量和明确标注的情景范围（不是统计置信区间）。
4. 点击刷新，展示按钮忙状态、更新时间和失败提示。

可以补充：筛选不是前端假过滤，而是传给 `/api/dashboard?product_id=...&store_id=...` 和 `/api/inventory?...`，后端重新按同一口径聚合。

## 2:20-3:20 模型可信度

打开 `/api/model-info`：

- 训练、验证、测试按时间切分，避免随机切分带来的未来信息泄漏。
- LSTM 捕捉序列模式，LightGBM 使用 lag、rolling、价格和日历特征。
- 集成权重为 `0.4 / 0.6`，报告同时保留两个子模型和集成指标。
- 7 日季节性朴素基线使用同商品同门店前一周同日销量，作为“复杂模型是否真的有收益”的参照。

然后打开 `/api/data-quality`，说明结果包含缺失值、重复键、日期断档和负销量检查。真实数据接入时，这个接口可以扩展为数据契约和训练前门禁。

## 3:20-4:20 工程取舍

推荐讲 3 个点：

1. **缓存**：销售 CSV、评估报告和单组合预测都有缓存，避免每次请求重复 IO 或推理。
2. **受控并发和失败隔离**：批量预测使用有上限的线程池，并按输入顺序返回；单个商品/门店失败会记录日志，不让整个 Dashboard 失效。
3. **可测试**：API、聚合口径、基线函数、报告兼容和前端关键控件都有自动化检查，Docker 启动后还可以用健康检查验证依赖。

## 4:20-5:00 主动说明边界

> 目前它还是 MVP：数据由脚本生成，模型是离线训练，文件存储也没有替换成真实数仓。下一步我会先建立真实数据契约和分层评估，再加定时训练、漂移监控、模型注册/回滚，最后根据部署规模引入队列、鉴权和更完整的可观测性。

主动讲边界会比只展示一个漂亮页面更能体现工程判断。

## 常见追问

### 为什么不用随机切分？

销售预测的目标是预测未来，随机切分会把未来分布混入训练集。按日期切分更接近上线时的时间顺序。

### 为什么需要基线？

没有基线就无法判断复杂模型是否真正超过简单方法。前一周同日基线还可以捕捉周周期，是零售场景中容易解释的参照。

### MAPE 有什么问题？

销量接近 0 时 MAPE 会不稳定，因此还报告 RMSE；真实项目还应按商品、门店和业务场景分层，并考虑 WAPE 或加权误差。

### 为什么集成后 RMSE 下降，但 MAPE 不是所有模型中最低？

MAPE 和 RMSE 对误差的惩罚方式不同。集成权重目前是固定的，下一步可以在时间验证集上调权，并用业务成本函数评估缺货与积压的非对称代价。

### 如果模型文件损坏怎么办？

健康检查会暴露依赖文件状态，预测服务会记录单个组合的失败。生产环境还应加入模型版本校验、注册表、回滚和启动前门禁。

### 这个项目离生产还差什么？

主要差在真实数据接入、持续训练与漂移监控、权限与密钥、多副本部署、推理队列和可观测性，而不是再堆一个更复杂的模型。
